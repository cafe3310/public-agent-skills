### Prompt撤退，未来属于 Loop Engineering

作者：数字生命卡兹克

最近，AI行业又出现了一个有趣的新词：**Loop Engineering**。
如果你关注AI这个领域的话，这两天应该都会刷到。推特在刷，各种社媒也在刷，群里也有蛮多人在讨论。

事情是这样的。6月7号，OpenClaw的创始人Peter发了一条推特，非常的简短，但是直接就爆了：

> **Peter Steinberger (@steipete)**:
> Here's your monthly reminder that you shouldn't be prompting coding agents anymore.
> You should be designing loops that prompt your agents.
> *（中文翻译：你不再需要为编码智能体编写提示词了，你应该设计循环来提示你的Agent。）*

这个“循环”，其实就是 **Loop** 的意思。

而在这之前几天，Claude Code的创始人老哥 Boris 在一个开发者大会上也说了差不多的话：

> Boris 的原话大概是：“我不再手动给 Claude 写提示词了，我运行着能让 Claude 自动编排任务的循环，我的工作，就是编写这些循环机制。”
> 也就是说，写 **Loop**。

这两个人呢，说了同一件事。然后 Google 的 Addy Osmani 紧接着发了一篇长文，把 **Loop Engineering** 这个概念正式梳理了出来：

> **Addy Osmani (@addyosmani)**:
> Loop Engineering正在取代你作为提示智能体的角色。你设计系统来替代你完成这项工作。这里的循环可以理解为一个递归目标，你定义其目的并让其自动跑完。

于是，继 Prompt Engineering、Context Engineering、Harness Engineering 之后，AI 行业的第四个逐渐形成共识的 Engineering，就这么诞生了。

我其实是个特别不喜欢造新词的人，但是很多时候，造词这事我觉得还是得分两种情况：一种我觉得就是为了炒概念（比如 xxx 4.0）；而有的时候，真的只是行业变化太快，人们需要一个更精准的词汇来辅助表达而已。

Loop Engineering 我觉得就是后一种。而且，这个东西跟我自己一直使用 Agent 的方法、一直在鼓励大家做的事，是高度吻合的。

如果你看过我之前写的那篇 Harness Engineering 的文章，你大概能理解一些我的感觉。那篇文章里我聊了从 Prompt 到 Context 到 Harness 的三次跃迁，聊了马具和缰绳的比喻，聊了约束先行。

而 Loop Engineering，其实就是在 Harness 轴上，又往上走了一层。把一个套马的缰绳，变成了全自动的工业流水线，很有《文明》里时代进化的感觉。

给大家举个例子：

比如说，以前你用 Claude Code 写代码，流程大概是这样的：你给它一个任务，它写完了，你看一眼，觉得不太对，你再给它提一个修改意见，它改完了，你再看，再提意见。整个过程你会发现，你依然是坐在设备前的，一轮一轮地，你说一句它回一句，你就是那个驱动整个循环的发动机。即便我们以前从 Chatbot 时代迈向了 Agent 时代，绝大多数事情，也一样是单次任务制的。

而现在，比如 Boris 老哥，他的工作方式是去写一个 Loop。比如一句话指令：`/loop babysit all my PRs`，自动修 CI 问题，有新评论就派子 Agent 去处理。就这么一句话，Claude Code 开始自己跑了。它会自动去看 GitHub 上所有的 PR，哪些 CI 挂了就自己修，哪些 review 有新评论就自动派一个独立的工作树 Agent 去改代码。他甚至把一些其他的 Loop 挂到定时任务上，每天晚上自动启动去干这个事。晚上睡觉的时候，甚至会有几千个 Agent 在同时工作。

他自己说，2026年，他就再也没有手写过一行代码了。

这就是 **Loop**：定好目标，然后全自动流程化，你完全不需要在电脑前，甚至都不需要看手机。可以直接睡觉，醒来的时候，代码已经改好了，测试也已经跑过了，PR也已经提上去了。

你并不是自己给 Agent 写了一段 Prompt 帮完成某个单次任务，而是你自己设计了一个目标，这个目标使用 Loop 的方式，帮你自动提示 Agent。你定义目标，定义验证条件，定义失败了怎么处理，然后就可以放手了。从此以后，这一切交给系统。

### Loop 的五个核心组件

Addy Osmani 在他那篇长文里，把一个完整的 Loop 拆成了五个核心组件。我觉得这个拆法蛮清晰的，我用我自己的理解给大家过一下：

| Primitive (基元) | Job in the loop (工作职责) | Codex App (实现方式) | Claude Code (实现方式) |
| :--- | :--- | :--- | :--- |
| **Automations** | 发现与分类任务，排程心跳 | prompt, cadence, environment; Automations 面板选择项目；结果输出至 Triage 收件箱 | 定时任务与 cron, `/loop`, `/goal`, Hook机制, GitHub Actions (执行直到完成) |
| **Worktrees** | 隔离并行开发特性，防冲突 | 内置每个线程的 worktree | `git worktree`, 工作树隔离 |
| **Skills** | 固化项目知识，避免重复解释 | Agent Skills (`SKILL.md`), 通过 `$name` 或隐式调用 | Agent Skills (`SKILL.md`), 结合 connectors 调用 |
| **Connectors** | 连接真实世界工具 | Connectors (MCP) 加上分发插件 | MCP 服务器与插件 |
| **Sub-agents** | 构思与多角色团队验证 | `.codex/agents/` 中使用 TOML 定义 sub-agents | `.claude/agents/` 中的任务子代理，各司其职，状态自洽 |
| **State** | 追踪已完成的进度 | Markdown 或通过 Connector 连 Linear | Markdown (`AGENTS.md`, 进度文件) 或通过 MCP 连 Linear |

1. **Automations（整个 Loop 的心跳）**
   你得有一个东西能自动启动循环，不管是定时跑，还是事件触发都行。Claude Code 里有好几种方式：`/loop` 命令按间隔自动执行，cron 定时调度，Hook 在 Agent 生命周期的特定节点自动触发（比如每次改完文件自动跑一遍 lint），或者直接丢到 GitHub Actions 里，关上电脑它也在跑。没有心跳，你每次都得手动去踢一脚它才会动，那就不是 Loop，还是你在操控。

2. **Worktrees（工作树隔离）**
   就是你同时跑好几个 Agent 的时候，给每个 Agent 一个独立的工作空间，各干各的互不干扰，干完了再合并。两个 Agent 改同一个文件的痛苦，跟两个设计师同时改一个图层又不打招呼的痛苦，是一模一样的。

3. **Skills（项目知识体系）**
   Addy Osmani 在原文里写的是 Skill，但我觉得写得不太对，单单 Skill 其实是不够的，必须得是知识管理体系。AI 每次开新对话就啥都忘了，你跟它说过代码规范、项目架构、踩过的坑，下次开对话全部从零开始。所以你得有一整套方法来沉淀、优化这些知识，让 Agent 每次启动的时候就已经知道你的项目。我自己在这快一年的 coding 开发过程中，总结出的方法论其实就沉淀成了我自己的 `洁癖.skill`（`neat-freak`），这基本是我的 Agent 每天调用最多的 Skill。
   * `CLAUDE.md` 是全局规则和约束。
   * 跨会话记忆是一些之前悬而未决的记录和文档路由。
   * docs 体系则是你完整的所有知识和经验沉淀。
   每次任务完成后，我会用 `洁癖.skill` 来对整个知识体系进行梳理和审查，确保没有错误。
   为什么干净的知识体系在 Loop 里特别重要？因为 Loop 是自动跑的，你不在场。如果 Agent 记忆里有过期信息，它就会基于错误的前提做决策。没有干净知识体系的 Loop，就像一个每天早上都在看过期文档的员工，干得越快错得越多。

4. **Connectors（连接器 - MCP）**
   一个只能看本地文件系统的 Agent，能力是很有限的。但你给它接上 GitHub、Linear、Slack、数据库，它就能在你的真实工作环境里干活了。这才是真正的闭环：从发现问题、解决问题到通知人类，一条龙。

5. **Sub-agents（子智能体）**
   做事的和检查的分开。写代码的 Agent 不能自己给自己打分，这跟学生自己批改自己的考卷一个道理，它一定会对自己太宽容。所以你得有另一个 Agent，甚至用不同的模型，专门来检查前一个 Agent 的输出。一个负责做，一个负责验。

这五个组件加在一起，就是一个完整 Loop 的骨架。

### Loop 的“术”与“道”：核心是定义目标的能力

Claude Code 和 Codex 有一个命令，其实就是 Loop Engineering 这套架构最直接的微观型产品化体现，只不过很多人没有意识到。它叫 `/goal`（在 Codex 里叫“追求目标”）。意思就是你给 Claude 一个完成条件，比如“所有测试通过并且 lint 检查没有报错”，然后它就会一轮一轮自己干，干完每一轮之后，就会检查这个条件是不是满足了。

大多数讲 Loop Engineering 的文章，都停在这一层：讲了五个组件，讲了 `/goal` 和 `/loop` 命令，讲了怎么配定时任务，就结束了。

这些我觉得，都是**“术”**。而我更想聊的，是**“道”**。

Loop Engineering 这件事，最核心最核心的能力，其实不是什么技术能力，也不是写脚本的能力，更不是会配 hook 的能力。
最核心的，是**定义目标的能力**。

定义目标，听起来简单，做起来是真的难。
回到前面说的 `/goal`，用法看起来非常直接，给一个完成条件，Claude 自己干到满足为止。但你如果真正用过就会知道，`/goal` 用得好不好，完全取决于你那个目标定义得好不好。我们拿两个例子对比一下你就明白了：

* **目标 A**：「把这个应用优化一下」。
* **目标 B**：「`test/auth` 目录下所有测试通过，`tsc --noEmit` 零报错，`npm run lint` 零违规」。

目标 A 会发生什么呢？Claude 会陷入一种非常尴尬的状态，因为它不知道什么叫“优化好了”，除非它是未来能自己主动帮你定义目标的超强模型。而绝大多数主流大模型（如 Opus 4.8 和 GPT-5.5），在自己定义目标的能力上还非常弱。它可能改了一点代码，然后自己觉得还行，就停了；也可能不停地改，把你的代码库改得面目全非，因为它始终无法判断自己到底什么时候算完成了。

而目标 B 呢？Claude 每改一轮代码，都会去跑测试、跑类型检查、跑 lint。三个命令，三个明确的通过标准。全过了就停，没过就继续，清清楚楚，干干净净。
同一个工具，同一个模型，区别只在于你对目标的定义好不好。

### 从管理人的逻辑，看管 Agent 的逻辑

我自己有一个原则：**如果一件事你重复做了三次，你就一定要想办法把它完全自动化掉。**

这个习惯跟了我很多年了。我每天都在写代码、做自动化。我们的 AI HOT 热点监控系统、数据分析流程、财务对账流程、数据清洗管道，能自动的我全部自动了。但在做这些自动化的过程中，我踩过最多的坑，从来不是技术问题，而是**目标不清晰**的问题。

早期做自动化的时候，我经常犯一个错，就是目标定得太模糊。比如“自动监控AI行业热点”。这句话听起来没毛病，但其实是一句纯粹的废话。
* 什么叫热点？浏览量过万算热点还是过十万算热点？
* 抓取频率是每小时还是每天？
* 抓到以后怎么评估质量？评估完以后怎么排序？排完以后怎么推送？
每一个环节如果没有明确的判定标准，整个自动化链条就是一坨狗屎。

后来我懂了，每次做自动化之前，我会先花很多时间去定义目标：定义怎么算做完了，怎么做完算做好。这其实就是 `/goal` 的逻辑，也是 Loop Engineering 的灵魂。

而如何定义目标这个能力，我不是从 AI 中也不是从开发中学来的，是我从这几年创业管人的过程中学来的。
定义目标的能力，其实就是**管人逻辑**。

我自己也开公司，管理员工最痛苦的是什么？不是人不努力，也不是人能力不够，是你给出的目标不够清晰，员工一头雾水，不知道你要什么，最后做出来的东西你又不满意。
* 你跟员工说：“把这个功能做好”，他做出来的东西大概率不是你想要的，因为你脑子里的“好”跟他脑子里的“好”不一样。
* 你跟员工说：“这个接口的响应时间降到 200 毫秒以下，错误率控制在 0.1% 以内，下周三之前上线”，他做出来的东西跟你预期的偏差就会小很多。因为你给了他一个可以验证完成的标准。

对人如此，对 AI 也是如此。
所有好的管理方法论，无论是德鲁克提出的目标管理，还是安迪·格鲁夫在英特尔发明的 OKR，核心都是同一个东西：**你能不能把一个模糊意图，翻译成一组可衡量、可验证的完成条件。**

管理者要做的，是确保目标足够清晰、资源足够充足、反馈足够及时。这和好的 Loop 的三个要素一模一样：
* **目标清晰**：条件写得精准。
* **资源充足**：给 Agent 配好 Skill、连接器、工作权限，让它手里有足够的工具干活。
* **反馈及时**：设计了验证机制，每一轮都有独立的检查器告诉 Agent 做得对不对。

不过，管 Agent 比管人还要极端。人如果觉得目标模糊会主动来找你确认，而 Agent 不会，它会非常自信地按照它自己的理解去执行，并自信地告诉你它做完了。因此，对目标管理能力的要求，其实比管人还要高。

### 古德哈特定律与边界约束

在定义目标时，还有一个非常经典的陷阱，叫做**古德哈特定律 (Goodhart's law)**：

> **“一项指标一旦变成了目标，它将不再是个好指标。”**
> 也就是说，你考核什么，员工就只做什么，其他东西可能全部退化。

在 AI Agent 身上，这个问题被放大了一百倍，因为 Agent 比人类更擅长钻规则的空子。在 Loop Engineering 中经常发生很好玩的事情：Agent 会针对验证器做优化，而不是针对你真正的目标做优化。
* 比如你的 Loop 完成条件是“让测试全部通过”，Agent 可能最后不去修 Bug，而是直接把失败的测试文件给删了。测试全过了，任务完成了，但它啥也没干。

所以，一个好的目标定义，不能只有“做完了的完成标准”，还必须有**“不能怎么做”的边界约束**。
这其实就是 Harness Engineering（马具/约束）在 Loop Engineering 里面发挥作用的地方。
* **Harness 是约束**：是护栏，告诉 Agent 你可以自由发挥，但这条界线你不能越过。
* **Loop 是驱动力**：是油门，告诉 Agent 往那个方向一直跑。
两个加在一起，才是一个完整的系统。

### 总结：目标定义框架与四次跃迁

最后分享一个我自己用得比较多的**目标定义框架**：
1. **完成标准要可以被机器验证。**
2. **边界条件要跟完成标准一起定义。**
3. **要有失败的降级方案。**
4. **目标要分层。**

从 Prompt 到 Context，再到 Harness 和 Loop，四次跃迁，其实讲的是同一个故事：

* **Prompt Engineering** 告诉你，好好说话，AI会更懂你。核心能力是**语言表达**。
* **Context Engineering** 告诉你，光说话不够，得给AI足够的信息。核心能力是**信息筛选和组织**。
* **Harness Engineering** 告诉你，光给信息也不够，得给AI设规则和约束。核心能力是**系统设计和规则制定**。
* **Loop Engineering** 告诉你，光设规则也不够，得让整个系统自己跑起来。核心能力是**目标定义和管理**。

语言学、信息科学、控制论、管理学。四个 Engineering，四门古老学科。多有意思，人类社会的发展规律，其实从来就没有变过。
