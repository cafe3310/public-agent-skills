# [项目/功能名称] 产品需求文档 (PRD)

> PRD 的核心是 **清晰、准确、无歧义** 地传递需求。确保任何读到这份文档的干系人（产品、设计、开发、测试、运营）都能对要做什么、为什么做以及验收标准达成一致。

---

## 1. 背景 (Background)

> **“为什么我们现在要做这件事？”**
> 
> 这是整个文档的开篇，需要用简洁的语言和数据让所有人快速理解项目的缘起和价值。

```text
【说明】
这一部分需要清晰地阐述项目启动的上下文和动机。通常包含以下几点：

1.  **现状与数据：** 当前业务或产品的状态是什么？用关键数据（如 DAU、转化率、用户反馈数量等）来量化现状。
2.  **问题与挑战：** 基于现状，我们遇到了什么问题、瓶颈或挑战？
3.  **机遇与价值：** 解决这些问题能带来什么业务价值或用户价值？市场或用户是否出现了新的机会？
4.  **需求来源：** 明确需求的最初来源，是来自用户反馈、高层战略、数据分析，还是市场竞争等。
```

## 2. 产品愿景与目标 (Product Vision & Goals)

> **“我们最终希望达成什么？衡量成功的标准是什么？”**
>
> 这部分定义了项目的北极星，确保所有努力都朝向一个共同的长期方向。

### 2.1 终极愿景 (Ultimate Vision)

```text
【说明】
用一句话或一段话，描绘出该产品或功能在未来最理想的状态。它应该是鼓舞人心、具有前瞻性的。
```

### 2.2 核心目标 (Core Goals)

```text
【说明】
将愿景拆解为更具体、可衡量的目标。建议遵循 SMART 原则（具体、可衡量、可实现、相关、有时限），或至少是可量化的。

可以从不同维度设定目标：
- **用户目标：** 用户能通过产品完成什么？（例如：让 Prosumer 用户能够轻松创造并分享 AI 应用）
- **业务目标：** 产品希望达成什么业务指标？（例如：付费转化率提升 X%、开发者社区月活达到 Y）
- **产品目标：** 产品自身需要达到什么标准？（例如：核心链路性能优于竞品 Z）
```

## 3. 产品路线图 (Product Roadmap)

> **“我们将如何分阶段实现目标？”**
>
> 这部分展示了产品的迭代计划，让团队对未来有清晰的预期。

```text
【说明】
以“里程碑”或“阶段”的形式，规划出从当前版本到实现最终愿景的路径。每个阶段都应包含：

- **阶段名称 (Phase Name):** 例如，“第一期：专业级模型试验场”。
- **核心目标 (Goal):** 这个阶段最核心的目的是什么？
- **核心功能 (Core Features):** 这个阶段计划交付的关键功能点列表。

例如：
**第一期：XX**
- 目标：...
- 核心功能：
  - 功能 A
  - 功能 B

**第二期：YY**
- 目标：...
- 核心功能：
  - 功能 C
  - 功能 D
```

## 5. 本期需求详述 (Requirements for This Phase)

> **“这个阶段我们具体要做什么，以及它应该是什么样子？”**
>
> 这是 PRD 的核心，需要详细、无歧义地描述本期要做的每一个功能。

```text
【说明】
为本期的每一个核心功能创建一个二级标题（例如 "## 5.1 功能 A：用户账户体系"）。
在每个功能标题下，应详尽描述其需求，建议包含以下元素：

1.  **功能描述 (Description):** 用一小段话说明这个功能是做什么的，为用户/业务带来什么价值。
2.  **设计稿/线框图 (Mockups/Wireframes):** 嵌入 UI/UX 设计稿的图片或链接。**一图胜千言**。
3.  **用户流程/故事 (User Flow/Story):** 描述用户如何与该功能进行交互。
    -   例如：“当用户点击「保存」按钮时，系统会...”
4.  **详细规则/规格 (Detailed Rules/Specifications):**
    -   **UI 元素说明：** 按钮状态、文案、交互反馈等。
    -   **参数/数据定义：** 对于涉及输入输出的字段，用表格定义其名称、说明、格式、范围、默认值等。
    -   **逻辑规则：** 清晰地描述各种逻辑判断，特别是边界条件和异常情况。
        - **正常流程：** 用户按预期操作时，系统如何响应。
        - **异常流程：** 当出现错误（如网络中断、输入非法）或用户执行非标准操作时，系统应如何处理（如错误提示文案、回退机制）。
5.  **数据埋点 (Data Tracking):** 需要追踪哪些用户行为，以供后续分析。
```

## 6. 功能总览清单 (Feature Checklist)

> **“本期所有工作项的快照。”**
>
> 这是一个总结性的清单，方便开发进行任务拆解、测试编写用例、项目经理跟进进度。

```text
【说明】
用一个总表来概览本期涉及的所有功能点。

| 功能分类 | 功能点 | 本期变更说明 | 优先级 |
| -------- | ------ | ------------ | ------ |
| 账户体系 | 邮箱注册 | ++ 新增功能   | P0     |
|          | 手机号登录 | ~ 优化流程   | P1     |
| 模型对话 | 参数配置 | ++ 新增功能   | P0     |
|          | 文件上传 | - (本期不做) | -      |

- **功能分类 (Category):** 功能所属的模块。
- **功能点 (Feature):** 具体的功能项。
- **本期变更说明 (Change Description):**
  - `++ 新增功能`: 从 0 到 1 实现的功能。
  - `~ 优化/变更`: 对现有功能的修改。
  - `- (本期不做)`: 明确本次范围不包含的内容，防止范围蔓延。
- **优先级 (Priority):** P0/P1/P2，用于研发排期。
```

## 7. 非功能性需求 (Non-functional Requirements)

> **“除了看得见的功能，我们还有哪些要求？”**

```text
【说明】
描述那些与具体功能无关，但同样重要的系统级要求。

- **性能 (Performance):** 页面加载时间、API 响应时间等。（例如：核心页面 LCP < 2.5s）
- **安全性 (Security):** 数据加密、防注入等。
- **兼容性 (Compatibility):** 需要支持的浏览器、操作系统、分辨率等。
- **国际化 (i18n):** 需要支持的语言。
```
