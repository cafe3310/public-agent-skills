# PRD Writer Skill 工作流与最佳实践

本文件旨在详细阐述 `prd-writer` Skill 的标准工作流程，其核心任务是将用户的高阶需求，通过结构化的分析与沟通，转化为一份详尽、可执行的产品需求文档（PRD）。

## 核心理念

本 Skill 的目标不仅仅是“写一个文档”，而是**主导一个结构化的对话**。这个对话过程旨在澄清需求、对齐多方认知、并在投入开发前识别和规避风险。Agent 在此流程中扮演着商业分析师、产品经理和技术文档工程师的综合角色。

## 7步工作流

### 第一步：收集项目信息

- **目标：** 对项目建立完整、全面的上下文认知。
- **行动：**
    - 使用 `search_file_content` 和 `glob` 工具，查找与项目名称或核心功能相关的所有文档、笔记和讨论记录。
    - 搜索范围应尽可能广泛，关键词可包括项目的代号、正式名称或关联的系统。
    - 仔细阅读用户的初始请求，提取关键术语用于搜索。

### 第二步：筛选高阶背景与现状

- **目标：** 将收集到的碎片化信息，提炼成一幅关于项目愿景、目标和当前状态的连贯图景。
- **行动：**
    - 从搜索结果中，识别并阅读描述**产品愿景、长期路线图和总体目标**的文档。
    - 识别并阅读描述**项目现状（"as-is"）**的文档，例如最近一个已完成版本的 PRD 或技术规格文档。
    - 重点关注长期愿景与当前现实之间的差距。

### 第三步：生成“现状分析”文档

- **目标：** 与用户确认你对项目背景的理解，并建立一个共同的沟通基线。
- **行动：**
    - 撰写一份新的 Markdown 文档（命名格式：`YYYY-MM-DD-项目名-Current-State.md`）。
    - 在文档中，综合你在第二步的发现，总结以下内容：
        - 项目的整体愿景。
        - 路线图中的关键里程碑。
        - 最近一个已完成版本（如 MVP）的功能与范围。
    - 将这份总结文档提交给用户，以验证其准确性。

### 第四步：获取用户对下一迭代的洞察

- **目标：** 理解用户对*下一个*开发周期的具体目标和想法。
- **行动：**
    - 请用户提供他们为下一迭代准备的需求、想法或“主观分析”。
    - 这是最关键的输入环节。用户的请求是*新*需求的最高优先级信息来源。

### 第五步：分析、对齐并生成“迭代分析”文档

- **目标：** 对比项目既有背景，审查用户的新需求，并制定一份前进计划。
- **行动：**
    - 评估用户的新想法（来自第四步）与项目背景（来自第三步）的一致性。
        - 这些想法是否与整体愿景对齐？
        - 它们是否是基于当前状态合乎逻辑的下一步？
        - 它们的范围是否合理？
    - 撰写一份新的分析文档（命名格式：`YYYY-MM-DD-项目名-Next-Iteration-Analysis.md`）。
    - 在文档中，逐点详述你的分析，确认每个提议功能的合理性与一致性。
    - 这份文档是连接用户原始想法和结构化 PRD 的桥梁。

### 第六步：识别参考资料并选择模板

- **目标：** 为撰写最终的 PRD 准备所有必要的组件。
- **行动：**
    - **识别参考资料：** 在第五步的分析文档中，创建一个章节，列出撰写 PRD 时应引用的所有源文档。这包括愿景文档、现状总结、用户输入、你的分析文档以及任何相关的技术规范。
    - **选择模板：**
        - 使用 `read_file` 检查上一迭代的 PRD，以理解其结构和风格。
        - 如果存在一个好的范例，就以它为模板。
        - 如果没有，则使用本 Skill 在 `assets/PRD-Template.md` 中提供的通用模板。

### 第七步：起草 PRD

- **目标：** 生成下一迭代的、完整的最终版 PRD。
- **行动：**
    - 为 PRD 创建一个新文件（命名格式：`YYYY-MM-DD-项目名-Next-PRD.md`）。
    - 使用选定的模板，综合所有已收集的信息进行撰写：
        - **背景、愿景、目标：** 从“现状分析”文档（第三步）中提取。
        - **本期需求详述：** 使用“迭代分析”文档（第五步）中的详细分析来撰写具体的功能描述。
        - **功能总览清单：** 在总览表中总结新功能。
    - 将起草好的 PRD 提交给用户，进行最终审核和修改。
