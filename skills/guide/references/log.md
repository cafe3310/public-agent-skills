# Subcommand: `/guide log` (一键记录日志、更新 TODO 并提交变更)

## 1. 核心意图与定位

`/guide log` 是一键式任务闭环与阶段收尾指令，等同于用户明确指示：
> **“你按 /guide 的指示记录开发现状到 backlog，更新 TODO.md，如果我们已经消费了 HANDOFF.md 则删除它，如果我显著提出了长期开发规约则记录新的 spec。然后 add 和 commit 提交所有变更代码；最后简单汇报。”**

---

## 2. 标准执行步骤

### 步骤 1：记录开发现状到 backlog
1. 确定日志标题（优先使用用户传入的参数，未传入时自动提炼 5~10 字精炼标题）；
2. 获取当前时间（`YYYY-MM-DD-HH-mm`），在 `{文档目录}/` 下创建 `YYYY-MM-DD-HH-mm-开发日志-{标题}.md`；
3. 撰写标准 Frontmatter（`title`, `date_created`, `creator`, `background`, `references`）；
4. 正文精炼记录：
   - **实质变更**：实现了哪些功能点、修改/新建了哪些核心文件（附带 `file://` 链接）；
   - **问题与修正**：遇到的关键问题、排查思路与最终修复方式；
   - **Spec 架构合规与测试验证**：对照的 Spec 规范、测试清单执行结论；
   - **后续建议**：建议的下一步任务。

### 步骤 2：更新 `TODO.md`
1. 将 `TODO.md` 中对应已完成的任务项由 `[ ]` 勾选为 `[x]`；
2. 若开发过程中识别出新的衍生待办，在对应章节追加。

### 步骤 3：消费并清理 `HANDOFF.md`
1. 检查项目根目录下是否存在上一个 Session 遗留的 `HANDOFF.md`；
2. 若本次会话已充分消费并完成了交接文档中的任务，则删除 `HANDOFF.md`，避免陈旧的交接上下文对后续会话产生误导。

### 步骤 4：长效开发规约沉淀（询问确认原则）
1. 检查本次交互中用户是否显著提出了长期生效的架构规则、开发禁忌或数据契约；
2. 若识别到潜在的长效 Spec，按**合理抽象原则**提炼概要，**向用户明确询问并获得确认后**，再沉淀至 `{规范目录}`（默认 `specs/`）对应文件中。

### 步骤 5：执行 Git Add & Commit
1. 执行 `git add` 将本次所有修改及新创建的文档、代码变更纳入暂存区；
2. 自动生成规范、精炼的 Conventional Commit Message（例如 `feat(config): ...`、`fix(time): ...`、`docs: ...`）；
3. 执行 `git commit`（默认不执行 `git push`，保留本地安全控制权）。

### 步骤 6：极简汇报
向用户输出简洁平实的收尾汇报：
- 开发日志文件路径（`file://` 链接）；
- `TODO.md` 更新状态；
- `HANDOFF.md` 清理情况；
- Git Commit Hash 与提交说明。
